# Credit risk model: a 12-month probability of default, built and validated in Pulse

**Audience:** risk-analytics lead. **Everything below was computed by Pulse** (`pulse api predict`, `pulse api process`, `pulse api compose`, `pulse explain`, `pulse synth`). Every figure is copied from a response in [`results/`](results/); the request that produced it is in [`req/`](req/).

> **Pulse version.** The cohort spec uses rule draws (`bernoulli()`, `uniform()`) and `"output": false` helper fields, which arrive in the Pulse alpha after v1.0.0-alpha.33 (the synth-realism work, roadmap U52). The casebook `Makefile` still pins alpha.33; build Pulse from a checkout that has U52 until the pin moves (see [REPRODUCE.md](REPRODUCE.md)).

## The business question

A consumer lender has 60,000 historical loan applications and knows which loans defaulted (90+ days past due or charged off) within 12 months. The questions:

1. Which application-time attributes drive 12-month default, and by how much?
2. Can a scorecard built only from information available **at application** rank-order risk on loans it never saw, and is it calibrated?
3. Which fields in the warehouse would make the model look better than it is, and how big is that illusion?

## Headline findings

| # | Finding | Evidence |
|---|---|---|
| 1 | The clean model rank-orders held-out loans monotonically: the default rate climbs from **1.83%** in the lowest-risk decile to **32.61%** in the highest, a lift of **2.66**. | Step 13 |
| 2 | It is calibrated: mean predicted PD on the 18,000-loan holdout is **12.21%** against an observed default rate of **12.27%**. | Step 14 |
| 3 | Its holdout AUC is **0.7360** (Gini 0.472, DeLong 95% CI 0.7256–0.7465) and its KS **0.351**, against **0.7398** and **0.360** for the true default probabilities used to simulate the data. It captures nearly all the separation the application data allows. | Step 14 |
| 4 | Adding two post-outcome fields (the bureau score re-pulled at month 12 and the collections flag) moves pseudo-R² from **0.114** to **0.861** and holdout AUC to **0.993**. The model then looks excellent and is unusable at origination. Ridge shrinkage does not hide the leak. | Steps 8, 8b, 8c, 13b, 14 |
| 5 | Pulse flags a naive target encoding as a leakage risk (`PULSE_FEAT_TARGET_LEAKAGE_RISK`) at predict time, before any data is read. One parameter, `fit_on: "split == 0"`, makes the encoding train-only (with `folds: 5` out-of-fold on the training rows), and stepwise selection keeps it. | Steps 7, 10, 11 |
| 6 | No number is copied between steps. The holdout is scored by Compose `fits` + `ATTR_REG_PREDICT`, the purpose encoding by `FEAT_TARGET_ENCODE`, and the scorecard's predictor list by `selection: "stepwise"` inside the fit itself. | Steps 10–14 |
| 7 | Money stays exact. Principal sums are `decimal128` to the cent ($724,849,873.00 across the book, and the two splits reconcile to that cent), by type rather than by luck. | Steps 1, 6 |

## Dataset

The cohort is synthetic and generated by Pulse itself (`pulse synth from-schema`, spec [`data/loans.synth.json`](data/loans.synth.json), seed `20240630`). The output is byte-identical on every run. It has 60,000 rows and 20 fields. 5,316 candidate rows were rejected and redrawn by the spec's affordability constraints (income at least $15,000; loan from $1,000 to $40,000 and at most 50% of income).

| Field | Type | Meaning |
|---|---|---|
| `loan_id` | u32 | Application identifier |
| `application_date` | date | Booking date, 2022-01-01 to 2024-06-30 |
| `state` | categorical_u8 | 15 states + `OTHER` (no true effect: a nuisance variable) |
| `purpose` | categorical_u8 | 40 stated purposes with a long tail (smallest has 57 loans) |
| `fico_score` | u16 | Bureau score at application (normal, mean 695, sd 55, clamped 560–850) |
| `credit_band` | categorical_u8 | A–G, cut from `fico_score` at 760/720/690/660/630/600 |
| `term_months` | u8 | 36 (72%) or 60 (28%) |
| `interest_rate` | f64 | Priced off band (A 7.0% … G 27.5%), +1.8 pts for 60 months, plus noise |
| `annual_income` | **decimal128(18,2)** | USD, log-normal (median ≈ $63k) |
| `loan_amount` | **decimal128(18,2)** | Funded principal, USD |
| `dti` | f64 | Debt-to-income %, 2 decimals |
| `revol_util` | f64, nullable | Revolving utilisation %; ~3% null (no revolving lines) |
| `emp_length_years` | u8, nullable | 0–10 years; ~6% null (not stated) |
| `home_ownership` | categorical_u8 | MORTGAGE / RENT / OWN / OTHER |
| `delinq_2yrs` | u8 | Delinquencies in prior 24 months (Poisson, mean 0.3) |
| `default_12m` | packed_bool | **Target** |
| `outcome` | categorical_u8 | Same outcome as a label (`performing` / `defaulted`), used to stratify the split and to split the KS test |
| `fico_at_month_12` | u16 | **Post-outcome**: score re-pulled 12 months after booking |
| `collections_flag` | packed_bool | **Post-outcome**: referred to collections |
| `recovery_amount` | decimal128(18,2), nullable | **Post-outcome**: USD recovered after charge-off; null if no default |

**Built-in ground truth.** The spec's rules compute each loan's true default probability in a helper field, `true_pd`, and draw the outcome with `bernoulli(true_pd)`. The helper is declared `"output": false`, so the file never carries it, and the post-outcome fields reuse one more helper, a shared `uniform()` draw, for the same reason. The logistic model is a known answer to check the fitted model against:

```
logit(PD) = -2.55 + band effect (A -1.3, B -0.7, C 0, D +0.45, E +0.85, F +1.2, G +1.5)
          + 0.035·(dti − 18) + 0.4·[60-month term] + 0.3·delinq_2yrs
          + (0.35 if employment length missing, else −0.03·years)
          + 0.2·[RENT] − 0.05·[OWN] + 2.0·(loan/income − 0.2) + 0.008·(revol_util − 50, if present)
          + purpose effect (small_business +0.7, franchise_fee +0.6, timeshare +0.5, tax_bill +0.45,
            legal_fees +0.4, medical +0.35, moving +0.3, … car −0.25; 23 purposes 0)
```

`fico_score` acts only through the band and `interest_rate` has no effect of its own: both are realistic but redundant candidates. `state` has no effect at all. The post-outcome fields are generated *from* the outcome, as in a real warehouse.

Because the true PD is a function of application-time columns the file does carry, steps 13 and 14 rebuild it in the request, with an `ATTR_FORMULA` (`true_pd`) holding the same logistic expression. It matches the generator's value to within 3 × 10⁻⁵ (income and principal are stored rounded to the cent, and the generator read them before rounding).

## Methodology

1. Profile the book and check data quality: nulls, exact money totals, segment default rates (steps 1–6).
2. Engineer features in Pulse's `features` slot: a seeded stratified 70/30 split, log transforms, one-hot band and housing, frequency-encoded purpose, and a train-only, out-of-fold target encoding of purpose. Row-level formulas in `attributes` add loan-to-income, missing-value indicators with imputations, and a 60-month flag.
3. Fit logistic regressions (`REG_GLM`, binomial/logit) on the **training split only**. Compare the clean candidate set with one that adds post-outcome fields, then let stepwise selection with BIC pick the scorecard, with Wald, bootstrap and grouped-jackknife standard errors.
4. Score the **holdout split** in one Compose batch: its `fits` train each model once on the training rows, and every holdout slot scores them per row with `ATTR_REG_PREDICT`. Check rank-ordering (decile table with share and lift), calibration (mean predicted vs observed), and separation (AUC with a DeLong interval, and two-sample KS between defaulters and non-defaulters).

All requests use `"cohort": {"filename": "loans.pulse", "data_dir": "."}` and run from this directory. `./run.sh` executes them in order. No request carries a number taken from another step's response.

**Exact money vs float.** The `decimal128` sums keep the cents, and the decimal mean keeps 4 decimal places (precision propagation, banker's rounding). Compare the running sum Pulse reports in `components` for the `f64` DTI column, whose every value has two decimals: `"sum": 1082157.02`. Pulse adds floats with a binned reproducible sum, so that total is the same on every worker count and shard split and shows no drift here. It is still a binary float, though: a value such as 0.1 has no exact float form, and a float column guarantees cents only as far as its rounding does. A `decimal128` column holds the cents themselves, so loan balances and recoveries are stored that way here.

`recovery_amount` is present on exactly the 7,359 defaulted loans. That is the first sign it is a post-outcome field (step 5).

### Step 7 — Pulse flags the target-encoding leak before anything runs ([`req/07_target_encode_predict.json`](req/07_target_encode_predict.json))

The obvious way to use a 40-level `purpose` in a logistic model is to replace each level with its default rate:

```json
"features": [
  {"type": "FEAT_TRAIN_TEST_SPLIT", "label": "split", "params": {"ratios": [0.7, 0.3], "seed": 42, "stratify": "outcome"}},
  {"type": "FEAT_TARGET_ENCODE", "field": "purpose", "label": "purpose_te", "params": {"target": "default_12m", "smoothing": 20}}
],
"filterers": [{"type": "FILTER_INCLUDE", "field": "split", "values": ["0"]}],
"regressions": [{"type": "REG_GLM", "name": "te_logit", "target": "default_12m",
                 "predictors": ["purpose_te", "fico_score", "dti"], "family": "binomial", "link": "logit"}]
```

`pulse api predict -r req/07_target_encode_predict.json --json` reads only the cohort header and schema, never a record, and returns:

```json
"warnings": [{
  "code": "PULSE_FEAT_TARGET_LEAKAGE_RISK",
  "message": "FEAT_TARGET_ENCODE without params.fit_on averages every record's outcome, the record's own and validation/test records' included; a preceding FEAT_TRAIN_TEST_SPLIT does not change that — set params.fit_on to the training rows (e.g. \"split == 0\"), optionally with folds for out-of-fold training values",
  "details": {"feature": "FEAT_TARGET_ENCODE", "feature_index": 1}}]
```

With `--strict` the same request is refused (`valid: false`). Filtering to `split == 0` does **not** make the encoding safe. Features run before filters, so every holdout loan's outcome is already inside the purpose means the model trains on. Any holdout evaluation of such a model is contaminated. (The request does run; the fitted `purpose_te` coefficient is 8.81 with pseudo-R² 0.087, but it is not used further.) The warning names the fix, which step 10 applies.

### Step 8 — Post-outcome fields make the model look far better than it is ([`req/08_leaky_vs_clean_fit.json`](req/08_leaky_vs_clean_fit.json))

Both models are fit on the training split with the same 22 application-time candidates. The second also receives the two post-outcome fields `fico_at_month_12` and `collections_flag`. Row-level helper columns come from `attributes`:

```json
"attributes": [
  {"type": "ATTR_FORMULA", "label": "lti",               "expression": "2.718281828459045 ** (log_loan - log_income)"},
  {"type": "ATTR_FORMULA", "label": "term60",            "expression": "term_months == 60 ? 1 : 0"},
  {"type": "ATTR_FORMULA", "label": "emp_missing",       "expression": "emp_length_years == nil ? 1 : 0"},
  {"type": "ATTR_FORMULA", "label": "emp_years",         "expression": "emp_length_years ?? 0"},
  {"type": "ATTR_FORMULA", "label": "revol_missing",     "expression": "revol_util == nil ? 1 : 0"},
  {"type": "ATTR_FORMULA", "label": "revol_util_filled", "expression": "revol_util ?? 50"}
],
"filterers": [{"type": "FILTER_INCLUDE", "field": "split", "values": ["0"]}],
"regressions": [
  {"type": "REG_GLM", "name": "clean_all_candidates",  "target": "default_12m", "family": "binomial", "link": "logit",
   "predictors": ["fico_score","band_B","band_C","band_D","band_E","band_F","band_G","interest_rate","term60","dti",
                  "lti","log_income","log_loan","delinq_2yrs","emp_missing","emp_years","revol_missing","revol_util_filled",
                  "home_RENT","home_OWN","home_OTHER","purpose_freq"]},
  {"type": "REG_GLM", "name": "with_post_outcome_fields", "...": "same 22 predictors + fico_at_month_12 + collections_flag"}]
```

(`lti` is (1 + loan)/(1 + income), rebuilt from the two `FEAT_LOG` columns.)

| Model (train, n = 42,000) | Deviance | Null deviance | McFadden pseudo-R² | IRLS iterations |
|---|---|---|---|---|
| 22 application-time candidates | 27,698.1 | 31,261.3 | **0.114** | 7 |
| … + `fico_at_month_12` + `collections_flag` | 4,358.4 | 31,261.3 | **0.861** | 10 |

Both fits converge. In the leaky model `collections_flag` takes a coefficient of +6.75 (SE 0.120) and `fico_at_month_12` −0.0936 (both p reported as 0). The application-time `fico_score` flips sign to +0.0919: the model is now reading the *change* in score, which is the outcome itself.

The same contrast on in-sample scores, using `ATTR_REG_FITTED` (a linear-probability fit per row) and `TEST_KS` between defaulters and non-defaulters ([`req/08b_in_sample_fitted_ks.json`](req/08b_in_sample_fitted_ks.json)):

```json
"attributes": [ "...helpers as above...",
  {"type": "ATTR_REG_FITTED", "label": "lpm_clean", "target": "default_12m",
   "predictors": ["fico_score","dti","lti","delinq_2yrs","revol_util_filled","emp_years","emp_missing","term60","home_RENT"]},
  {"type": "ATTR_REG_FITTED", "label": "lpm_leaky", "target": "default_12m",
   "predictors": ["...same 9...", "fico_at_month_12", "collections_flag"]}],
"tests": [{"type": "TEST_KS", "field": "lpm_clean", "split_by": "outcome", "label": "ks_clean_in_sample"},
          {"type": "TEST_KS", "field": "lpm_leaky", "split_by": "outcome", "label": "ks_leaky_in_sample"}]
```

| In-sample score (train) | KS statistic D | Defaulters / non-defaulters |
|---|---|---|
| Application-time predictors | 0.351 | 5,151 / 36,849 |
| … + `fico_at_month_12` + `collections_flag` | **0.939** | 5,151 / 36,849 |

A KS of 0.94 on consumer credit should trigger a leakage review. Step 13b shows the leaky model holds up on the holdout too, because the holdout carries the same leaked columns. A holdout cannot catch this kind of leak. Only checking *when* each field becomes known does.

### Step 8c — Side notes: the collections flag alone, and a ridge refit ([`req/08c_side_notes.json`](req/08c_side_notes.json))

```json
  {"type": "REG_GLM", "name": "with_post_outcome_fields_ridge", "...": "the step-8 leaky predictors",
   "penalty": "l2", "alpha": 0.01}]
```

**`default ~ collections_flag` alone** is a 2×2 table: on the training split 4,418 of 4,751 flagged loans and 733 of 37,249 unflagged loans defaulted. The logistic fit converges in 7 iterations to intercept −3.9084 and slope **+6.4937** (SE 0.0680, 95% CI 6.3604–6.6269), which are the closed-form logits: ln(733 / 36,516) = −3.9084 and ln(4,418 / 333) + 3.9084 = 6.4937. One post-outcome flag by itself reaches pseudo-R² **0.692**, six times the 22 honest candidates together.

**Ridge does not cure leakage.** The same leaky model refit with `penalty: "l2"`, `alpha: 0.01` (glmnet's objective, raw predictor units, intercept unpenalised) shrinks the `collections_flag` coefficient from 6.75 to 2.06, yet pseudo-R² is still **0.759**. A penalty limits how far a coefficient can grow; it cannot tell a field recorded after the outcome from one known at application.

### Step 9 — Stepwise selection with BIC ([`req/09_stepwise_bic.json`](req/09_stepwise_bic.json))

Same features, attributes, training filter and 22 candidates, with:

```json
{"type": "REG_GLM", "name": "pd_stepwise_bic", "target": "default_12m", "family": "binomial", "link": "logit",
 "predictors": ["...22 candidates..."], "selection": "stepwise", "criterion": "bic"}
```

BIC keeps 10 predictors (pseudo-R² 0.1119): `interest_rate, dti, lti, delinq_2yrs, revol_util_filled, emp_missing, emp_years, home_RENT, term60, fico_score`. It drops `log_income`, `log_loan` (`lti` carries them), `home_OWN`, `home_OTHER`, `revol_missing`, every band dummy (the rate and FICO carry them) and **`purpose_freq`**. How *common* a purpose is says nothing about how *risky* it is. Purpose needs an outcome-based encoding.

### Step 10 — Leak-free purpose encoding: `fit_on` and `folds` ([`req/10_purpose_te_train_only.json`](req/10_purpose_te_train_only.json))

One feature does what the naive encoder in step 7 cannot:

```json
{"type": "FEAT_TARGET_ENCODE", "field": "purpose", "label": "purpose_te",
 "params": {"target": "default_12m", "smoothing": 20, "fit_on": "split == 0", "folds": 5, "rng_seed": 11}}
```

- `fit_on: "split == 0"` takes the per-purpose means from the **training rows only** (it reads the split column the earlier feature made). Every row is encoded, holdout included, but no holdout outcome enters any encoding.
- `smoothing: 20` pulls each purpose toward the training default rate: `(defaults + 20 × 0.12264) / (n + 20)`. A 40-loan purpose is pulled most of the way back to 12.3%.
- `folds: 5` encodes each **training** row from the other four folds of training rows, so a loan's own outcome never feeds its own encoding. Holdout rows get the full-training value.

`pulse api predict` on this request returns `warnings: []` ([`results/10_purpose_te_train_only.predict.json`](results/10_purpose_te_train_only.predict.json)). Grouping by purpose and split shows the two behaviours (selected rows):

### Step 11 — Re-select with the safe purpose encoding ([`req/11_stepwise_bic_with_safe_te.json`](req/11_stepwise_bic_with_safe_te.json))

The step-9 request plus the step-10 feature, with `purpose_te` as a 23rd candidate. BIC now keeps **11 predictors**: the step-9 ten plus `purpose_te`, which is listed fifth in the selection order. Reading it:

- **The behavioural drivers recover the simulated truth closely.** Loan-to-income, delinquencies, DTI, utilisation, employment length and its missingness, and renting all sit within about two standard errors of the values the data was generated from.
- **The credit-quality block (rate and FICO) acts as a whole.** The interest rate is priced off the band, so the model carries the band effect through the rate and FICO, and no band dummy survives selection. The rate's coefficient is the band effect plus the term premium, not an effect of the rate itself (its true effect is zero). Do not read these coefficients one at a time.
- **The bootstrap agrees with the Wald SEs** to within about 4% on every term, so the asymptotic SEs can be trusted at this sample size. The bootstrap's percentile p-values are 0.001 for every slope (the floor for 1,000 replicates).
- **The 50-group jackknife is the fast check.** It needs 50 refits instead of 1,000 and adds about two seconds to the selection. With 49 degrees of freedom its SEs are themselves noisy, roughly ±20%: this draw is low on `lti` (0.120 against a Wald 0.138) and high on `emp_missing` (0.071 against 0.062). It agrees with the Wald SEs on the order of magnitude of every term, which is what a quick check needs.

## Findings and implications

1. **Use the 11-predictor scorecard for application decisions.** Affordability (loan-to-income, DTI), credit behaviour (delinquencies, utilisation), stability (employment length, and whether it was stated), housing, term, purpose and the priced credit grade all carry independent signal. Its holdout AUC (0.7360) and KS (0.351) almost match the best achievable on this data (0.7398 and 0.360, from the true PD), and its PDs are calibrated overall (12.21% vs 12.27%); by decile it overstates the riskiest tenth by 3.6 points.
2. **Missing data is information.** Applicants who leave employment length blank default at 18.71% vs 11.84%. Keep a missing-value indicator; do not drop the rows.
3. **Ban post-outcome fields from the modelling mart.** `fico_at_month_12` and `collections_flag` lift holdout AUC from 0.736 to 0.993 and pseudo-R² from 0.114 to 0.861; `collections_flag` alone reaches pseudo-R² 0.692. A random holdout does **not** expose this, because the leaked columns are in the holdout too, and a ridge penalty does not either. Each field needs an "available at decision time?" attribute in the data dictionary.
4. **Encode high-cardinality categoricals from training data only.** Pulse warns at predict time when `FEAT_TARGET_ENCODE` would use every row's outcome. With `fit_on: "split == 0"` and `folds: 5` the warning goes away, stepwise selection keeps the encoding, and frequency encoding of the same field is dropped as uninformative.
5. **Pricing variables are collinear with grade.** Rate and FICO carry the band effect between them. Report and monitor them as a block, not coefficient by coefficient.
6. **Keep money in `decimal128`.** Segment and split principal totals reconcile to the cent with the book total, by type. A float column's total is reproducible in Pulse, but exact cents are a property only `decimal128` guarantees.
